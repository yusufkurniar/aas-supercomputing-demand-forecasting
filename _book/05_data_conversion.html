6.1 Purpose

The purpose of this step is to convert historical High-Performance Computing (HPC) demand and allocation values into more comparable computational resource measures across reporting years, facilities, and systems.

The integrated dataset covers 13 financial years, from 2013/14 to 2025/26, and contains observations reported in different accounting units, including kilo service units (kSU), million compute hours, CPU core-hours, and GPU-related service units.

These observations originate from different HPC facilities and systems, including the National Computational Infrastructure (NCI) and Pawsey Supercomputing Research Centre. Historical system information includes Raijin, Magnus, FlashLite, MASSIVE, Gadi, and Setonix CPU and GPU resources.

Service-unit accounting conventions can vary across facilities, systems, resource types, and reporting periods. Consequently, values expressed in the same unit, such as kSU, are not necessarily computationally equivalent.

This stage therefore evaluates conversion rules at the system and resource level rather than applying a single conversion factor across the historical dataset.

Where sufficient documentation is available, original demand and allocation values are converted into CPU core-hours or GPU hours using the applicable accounting rules. Where conversion cannot be supported reliably, original values and their limitations are retained without introducing unsupported assumptions.

The conversion process preserves the original reported values, units, source references, derivation methods, and conversion assumptions to maintain transparency and reproducibility for subsequent exploratory analysis and forecasting.

6.2 Conversion Approach

The conversion process uses the standardised annual demand and allocation dataset produced in Chapter 04, together with the system-level resource information collected during Data Integration.

Each historical observation is assessed according to its reporting period, facility, HPC system, resource type, original accounting unit, and available conversion documentation.

The conversion process follows four principles:

  1. Preserve original observations. Original demand and allocation values, units, source references, and derivation assumptions are retained without modification.
  2. Identify resource-specific information. CPU and GPU resources are distinguished where supported by the original source records. Aggregate observations without a documented resource split remain unallocated to a specific resource type.
  3. Apply documented conversion rules. Conversion factors are selected according to the relevant system, resource type, and reporting period. No universal service-unit-to-compute-hour factor is assumed.
  4. Record conversion uncertainty. Where direct conversion rules or resource-level observations are unavailable, transparent assumptions are applied to produce estimated values. Each assumption is documented with its rationale, supporting evidence, confidence level, and limitations. Reported, derived, and assumed values remain distinguishable throughout the analysis.

The general relationship between kilo service units (kSU) and service units (SU) is:

\[ \text{SU} = \text{kSU} \times 1000 \]

However, conversion from service units to physical computational hours depends on the accounting rules of the relevant HPC system.

For example, CPU core-hours and GPU hours require separate conversion factors and cannot be combined directly into a single physical compute-hour measure.

The conversion framework therefore maintains separate demand and allocation measures and records conversion status, supporting evidence, and limitations for each observation.

Where system-level breakdowns are available, they will be assessed separately before aggregation. Historical observations lacking sufficient detail will not be assigned unsupported CPU/GPU proportions.

6.3 CPU Resources

CPU resource conversion translates historical service-unit allocations and reported compute hours into CPU core-hours.

The conversion is performed at the HPC system level where sufficient information is available. This is necessary because the accounting relationship between service units and CPU core-hours may differ across facilities and reporting periods.

For observations reported in kSU, CPU core-hours are calculated as:

\[ \text{CPU core-hours} = \frac{\text{CPU kSU} \times 1000} {\text{SU per CPU core-hour}} \]

For observations already reported in CPU core-hours, the original values are retained without applying an additional service-unit conversion.

Where aggregate kSU values include both CPU and GPU resources, the CPU component must first be identified or estimated before the conversion formula is applied.

The conversion framework considers the historical systems identified during Data Integration, including Raijin, Magnus, FlashLite, MASSIVE, Gadi, and Setonix CPU.

Documented accounting factors are prioritised. Where system-specific factors or resource splits are unavailable, assumptions are applied with explicit justification, source references, and confidence classifications.

All calculations preserve the original observations and distinguish directly reported CPU values from derived and assumed estimates.

# Historical CPU core-hour conversion: 2013/14–2018/19
# Assumption: 1 SU per CPU core-hour for historical CPU kSU
# Years already reported in millions of hours are scaled by 1,000,000

historical_cpu_share <- 1.0  # Baseline assumption: 100% CPU-equivalent

conversion_data <- conversion_data |>
  mutate(
    demand_cpu_core_hours = case_when(
      year == 2014 ~ demand_ksu * 1000 * historical_cpu_share,
      year %in% 2015:2019 ~ requested_compute * 1e6,
      TRUE ~ demand_cpu_core_hours

    allocation_cpu_core_hours = case_when(
      year %in% c(2014, 2015, 2016) ~
        allocation_ksu * 1000 * historical_cpu_share,
      year %in% 2017:2019 ~ allocated_compute * 1e6,
      TRUE ~ allocation_cpu_core_hours

      year == 2014 ~

6.4 GPU Resources

GPU resources are converted separately from CPU resources.

Where a documented GPU service-unit rate is available:

\[ \text{GPU Hours} = \frac{\text{kSU} \times 1000} {\text{SU per GPU Hour}} \]

GPU hours are not combined directly with CPU core-hours because they represent different types of computational resources.

6.5 Historical Conversion

Conversion of historical observations requires additional care because HPC systems and service-unit accounting methods have changed over time.

For each observation, the conversion process considers:

  • facility
  • HPC system
  • reporting period
  • resource type
  • original unit
  • documented service-unit accounting method

Where a reliable conversion factor cannot be identified, the original reported value is retained rather than applying an unsupported conversion.

6.6 Conversion Documentation

The converted dataset retains information about how each value was produced.

Where possible, this includes:

  • original reported value
  • original reported unit
  • converted value
  • converted unit
  • conversion formula or factor
  • conversion source
  • conversion confidence
  • comparability status
  • relevant notes

This allows converted values to be traced back to their original source and assumptions.

6.7 CPU and GPU Separation

CPU core-hours and GPU hours are maintained as separate measures throughout the analysis.

This avoids treating different computational resources as directly equivalent and allows changes in the composition of HPC demand, including increasing GPU demand, to be analysed separately.

6.8 Current Limitations

Conversion factors have not yet been confirmed for every historical system and year.

In particular, historical service-unit accounting and changes associated with system transitions require further validation. These assumptions will be reviewed using available documentation and feedback from NCI and Pawsey before the final converted dataset is used for modelling.

6.9 Output

The output of this step will be a conversion table and analysis dataset containing the original reported values together with comparable CPU or GPU measures where supported by sufficient evidence.

# Data Conversion

## Purpose

The purpose of this step is to convert historical High-Performance Computing (HPC) demand and allocation values into more comparable computational resource measures across reporting years, facilities, and systems.

The integrated dataset covers 13 financial years, from 2013/14 to 2025/26, and contains observations reported in different accounting units, including kilo service units (kSU), million compute hours, CPU core-hours, and GPU-related service units.

These observations originate from different HPC facilities and systems, including the National Computational Infrastructure (NCI) and Pawsey Supercomputing Research Centre. Historical system information includes Raijin, Magnus, FlashLite, MASSIVE, Gadi, and Setonix CPU and GPU resources.

Service-unit accounting conventions can vary across facilities, systems, resource types, and reporting periods. Consequently, values expressed in the same unit, such as kSU, are not necessarily computationally equivalent.

This stage therefore evaluates conversion rules at the system and resource level rather than applying a single conversion factor across the historical dataset.

Where sufficient documentation is available, original demand and allocation values are converted into CPU core-hours or GPU hours using the applicable accounting rules. Where conversion cannot be supported reliably, original values and their limitations are retained without introducing unsupported assumptions.

The conversion process preserves the original reported values, units, source references, derivation methods, and conversion assumptions to maintain transparency and reproducibility for subsequent exploratory analysis and forecasting.

## Conversion Approach

The conversion process uses the standardised annual demand and allocation dataset produced in Chapter 04, together with the system-level resource information collected during Data Integration.

Each historical observation is assessed according to its reporting period, facility, HPC system, resource type, original accounting unit, and available conversion documentation.

The conversion process follows four principles:

1. **Preserve original observations.** Original demand and allocation values, units, source references, and derivation assumptions are retained without modification.
2. **Identify resource-specific information.** CPU and GPU resources are distinguished where supported by the original source records. Aggregate observations without a documented resource split remain unallocated to a specific resource type.
3. **Apply documented conversion rules.** Conversion factors are selected according to the relevant system, resource type, and reporting period. No universal service-unit-to-compute-hour factor is assumed.
4. **Record conversion uncertainty.** Where direct conversion rules or resource-level observations are unavailable, transparent assumptions are applied to produce estimated values. Each assumption is documented with its rationale, supporting evidence, confidence level, and limitations. Reported, derived, and assumed values remain distinguishable throughout the analysis.

The general relationship between kilo service units (kSU) and service units (SU) is:

$$
\text{SU} = \text{kSU} \times 1000
$$

However, conversion from service units to physical computational hours depends on the accounting rules of the relevant HPC system.

For example, CPU core-hours and GPU hours require separate conversion factors and cannot be combined directly into a single physical compute-hour measure.

The conversion framework therefore maintains separate demand and allocation measures and records conversion status, supporting evidence, and limitations for each observation.

Where system-level breakdowns are available, they will be assessed separately before aggregation. Historical observations lacking sufficient detail will not be assigned unsupported CPU/GPU proportions.

## CPU Resources

CPU resource conversion translates historical service-unit allocations and reported compute hours into CPU core-hours.

The conversion is performed at the HPC system level where sufficient information is available. This is necessary because the accounting relationship between service units and CPU core-hours may differ across facilities and reporting periods.

For observations reported in kSU, CPU core-hours are calculated as:

$$
\text{CPU core-hours} =
\frac{\text{CPU kSU} \times 1000}
{\text{SU per CPU core-hour}}
$$

For observations already reported in CPU core-hours, the original values are retained without applying an additional service-unit conversion.

Where aggregate kSU values include both CPU and GPU resources, the CPU component must first be identified or estimated before the conversion formula is applied.

The conversion framework considers the historical systems identified during Data Integration, including Raijin, Magnus, FlashLite, MASSIVE, Gadi, and Setonix CPU.

Documented accounting factors are prioritised. Where system-specific factors or resource splits are unavailable, assumptions are applied with explicit justification, source references, and confidence classifications.

All calculations preserve the original observations and distinguish directly reported CPU values from derived and assumed estimates.

  mutate(
    demand_cpu_core_hours = coalesce(
      calculated_demand_cpu_core_hours,
      demand_cpu_core_hours
    )
  ) |>
  select(-calculated_demand_cpu_core_hours)

  all(!is.na(conversion_data$allocation_cpu_core_hours))

## GPU Resources

GPU resources are converted separately from CPU resources.

Where a documented GPU service-unit rate is available:

$$
\text{GPU Hours}
=
\frac{\text{kSU} \times 1000}
{\text{SU per GPU Hour}}
$$

GPU hours are not combined directly with CPU core-hours because they represent different types of computational resources.

## Historical Conversion

Conversion of historical observations requires additional care because HPC systems and service-unit accounting methods have changed over time.

For each observation, the conversion process considers:

- facility
- HPC system
- reporting period
- resource type
- original unit
- documented service-unit accounting method

Where a reliable conversion factor cannot be identified, the original reported value is retained rather than applying an unsupported conversion.

## Conversion Documentation

The converted dataset retains information about how each value was produced.

Where possible, this includes:

- original reported value
- original reported unit
- converted value
- converted unit
- conversion formula or factor
- conversion source
- conversion confidence
- comparability status
- relevant notes

This allows converted values to be traced back to their original source and assumptions.

## CPU and GPU Separation

CPU core-hours and GPU hours are maintained as separate measures throughout the analysis.

This avoids treating different computational resources as directly equivalent and allows changes in the composition of HPC demand, including increasing GPU demand, to be analysed separately.

## Current Limitations

Conversion factors have not yet been confirmed for every historical system and year.

In particular, historical service-unit accounting and changes associated with system transitions require further validation. These assumptions will be reviewed using available documentation and feedback from NCI and Pawsey before the final converted dataset is used for modelling.

## Output

The output of this step will be a conversion table and analysis dataset containing the original reported values together with comparable CPU or GPU measures where supported by sufficient evidence.
